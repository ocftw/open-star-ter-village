# Per-PR staging on Fly.io

Maintainers can deploy any open pull request to a throwaway Fly.io app named
`osv-pr-<number>`. The app runs in a separate Fly organization, never in the
production `open-star-ter-village` app.

## Using the `staging` label

1. Review the PR's latest commits, then add the `staging` label.
2. The **PR Staging** workflow deploys the exact head commit and posts one
   comment on the PR (it updates the same comment on later deploys) with:
   - `https://osv-pr-<number>.fly.dev`
   - `https://osv-pr-<number>.fly.dev/dev?seed=e2e-2` (the `/dev` harness,
     which staging images enable)
3. While the label stays on, each push redeploys automatically, but only if
   the pusher has write access too (see below).
4. To redeploy by hand, run **PR Staging** from the Actions tab with
   `pr_number`. The PR must be open and still carry the label.
5. Removing the label or closing the PR destroys the app. An hourly reaper
   (`pr-staging-reaper.yml`) also destroys any `osv-pr-*` app older than 4
   hours. Re-add the label to get a fresh one.

Limits:

- At most 5 `osv-pr-*` apps can exist at once. A sixth request gets a PR
  comment and the label is removed.
- Each app is a single `shared-cpu-1x` machine with 256 MB in `sin`, with no
  volume. It stops when idle and starts on the next request, so the first load
  is slow and in-memory matches are lost when it stops.
- Staging builds get no Google Tag Manager ID, Sentry DSN, or Discord webhook.

## Repository configuration

| Name | Kind | Purpose |
| --- | --- | --- |
| `FLY_STAGING_API_TOKEN` | Actions secret | Org-scoped deploy token for the staging Fly org only (`fly tokens create org`). |
| `FLY_STAGING_ORG` | Actions variable | Slug of the staging Fly org, for example `osv-staging`. |

The staging workflows never read the production `FLY_API_TOKEN`. Use a
separate Fly org so a leaked or misused staging token cannot reach production.
If either value is missing, deploys fail with an explanatory error, and
teardown and the reaper skip with a notice.

## Security: `pull_request_target`

Label events from fork PRs only expose secrets under `pull_request_target`.
That trigger runs with the base repository's secrets and a write-capable
`GITHUB_TOKEN`. Checking out and running untrusted PR code there is the
classic "pwn request". Here is how the workflow contains that risk:

- **Workflow code comes from `main`.** `pull_request_target` always runs
  `pr-staging.yml` and the reusable `permission-fence.yml` from the base
  branch, so a PR cannot change the gate it is judged by.
- **Permission fence first.** Every deploy path needs the fence job before any
  job checks out PR code or can read `FLY_STAGING_API_TOKEN`. The fence calls
  `GET /repos/{owner}/{repo}/collaborators/{actor}/permission` and allows only
  `admin`, `maintain` or `write`. Any other role, a lookup error, or a 404
  denies. The actor checked depends on the event:
  - label added: the person who added it;
  - push to a labeled PR: the pusher;
  - reopen: the person who reopened it;
  - manual dispatch: whoever triggered the run.
- **New commits from outsiders do not ride on an old approval.** When a fork
  author pushes to a labeled PR, the fence denies that push. The workflow then
  removes the label, explains why in a comment, and destroys any existing
  staging app. A maintainer must review the new commits and label again.
- **Exact SHA, no credentials.** Only the deploy job checks out PR code. It
  checks out the head SHA recorded at fence time (not the branch, which could
  move), with `persist-credentials: false` and a read-only `GITHUB_TOKEN`.
  Nothing from the PR is installed or executed on the runner. `flyctl` builds
  the Dockerfile on Fly's remote builder inside the staging org, using a Fly
  config generated by the workflow, never the PR's `fly.toml`.
- **Writes happen in separate jobs.** Comments and label changes run in a job
  with `issues`/`pull-requests: write` that never checks out PR code. Teardown
  jobs never check out code.
- **Destroy guard.** Every destroy path refuses any app name that does not
  match `^osv-pr-[0-9]+$` or that equals `open-star-ter-village`. Per-PR
  teardown also confirms the app is listed in the staging org first.

Residual risk: the code a maintainer labels runs in the staging org with no
secrets, so review before labeling. A manual dispatch deploys whatever the PR
head is at that moment.

## The `/dev` route

`/dev` returns 404 in production builds unless the image is built with
`ENABLE_DEV_ROUTE=true` (Docker build arg, default `false`). Only the staging
workflow sets it. The production deploy and the `e2e:production` check that
`/dev` returns 404 are unchanged.
